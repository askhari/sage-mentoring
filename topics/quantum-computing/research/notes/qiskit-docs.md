## qiskit-circuits
- A circuit is a set of qubits plus an ordered list of instructions. `QuantumCircuit(2)` creates 2 qubits. Instructions are stored in `circuit.data` as `CircuitInstruction` objects. (/docs/en/guides/construct-circuits) → qiskit-circuits
- Named `QuantumRegister` and `ClassicalRegister` objects can be combined in one circuit, and `find_bit` gives a bit's index and register. (/docs/en/guides/construct-circuits) → qiskit-circuits
- Standard gates are added with methods such as `qc.h(0)` and `qc.cx(0, 1)`. `append` adds any gate, for example `HGate` from `qiskit.circuit.library`. (/docs/en/guides/construct-circuits; /docs/en/guides/hello-world) → qiskit-circuits
- `depth()` counts layers of gates that can run in parallel, and it roughly reflects execution time. (/docs/en/guides/construct-circuits) → qiskit-circuits
- `compose` merges circuits, accepts a `qubits=` mapping, and returns a new circuit unless `inplace=True`. `to_instruction` and `to_gate` package a circuit as one operation, and `decompose` expands it again. (/docs/en/guides/construct-circuits) → qiskit-circuits
- Measurement: `measure` maps chosen qubits to chosen classical bits. `measure_all` creates the classical bits itself, in a register named `meas` by default, and inserts a barrier first. `measure_active` measures only qubits that have operations. (/docs/en/guides/construct-circuits; /docs/en/guides/primitive-input-output) → qiskit-circuits
- Sampler circuits need measurements. Estimator circuits must not contain any. (/docs/en/guides/construct-circuits) → qiskit-circuits, primitives-sampler-estimator
- Barriers: this guide mentions them only through `measure_all`. ⚠️ It has no standalone barrier section. → qiskit-circuits
- `Parameter` leaves a value undefined so that one circuit can be built and transpiled once and reused. `assign_parameters` returns bound copies, and the `parameters` attribute lists the unbound ones. `ParameterVector` makes named groups of parameters. (/docs/en/guides/construct-circuits) → qiskit-circuits
- Drawing: `qc.draw("mpl")` renders with Matplotlib. `cregbundle=False` shows each classical wire separately. (/docs/en/guides/construct-circuits) → qiskit-circuits
- Circuit library: ready-made circuits include `efficient_su2` (used as an ansatz) and `z_feature_map`. (/docs/en/guides/simulate-with-qiskit-aer; /docs/en/guides/construct-circuits) → qiskit-circuits
- Removed in 1.0: `qiskit.execute` is replaced by `transpile()` followed by `backend.run()`, or by a Sampler. (/docs/en/guides/qiskit-1.0-features) → qiskit-circuits
- Removed in 1.0: `qiskit.BasicAer` became `qiskit.providers.basic_provider`, with `BasicProvider`, `BasicSimulator` (was `QasmSimulatorPy`). `qiskit.Aer` and `qiskit.providers.aer` became the separate package `qiskit_aer`. (/docs/en/guides/qiskit-1.0-features; /docs/en/guides/metapackage-migration) → qiskit-circuits, simulators-and-statevectors
- Removed in 1.0: `bind_parameters()` became `assign_parameters()`. The gate aliases `cnot`, `toffoli`, `fredkin`, `mct` became `cx`, `ccx`, `cswap`, `mcx`. `QuantumCircuit.qasm()` became `qasm2.dump`/`dumps`. `qiskit.extensions` moved into `qiskit.circuit.library`. (/docs/en/guides/qiskit-1.0-features) → qiskit-circuits
- Removed in 2.0: legacy `c_if` conditions are replaced by the `if_test` context manager (or the `expr` module). `Instruction.duration`/`unit` are removed, so use `Target` durations or `QuantumCircuit.estimate_duration`. The whole `qiskit.pulse` module is removed, because IBM QPUs no longer offer pulse access; fractional gates on Heron QPUs replace it. (/docs/en/guides/qiskit-2.0) → qiskit-circuits
- Packaging: since 1.0 Qiskit is the single distribution `qiskit` (`qiskit-terra` is retired), and `pip install qiskit` no longer pulls in `qiskit-aer`. A fresh virtual environment is recommended rather than an in-place upgrade. Since 2.0 only 64-bit platforms are supported. (/docs/en/guides/metapackage-migration; /docs/en/guides/install-qiskit) → qiskit-circuits

## simulators-and-statevectors
- `StatevectorEstimator` and `StatevectorSampler` (in `qiskit.primitives`) are the reference primitives. They run ideal local statevector simulation and cannot model device noise, so they suit prototyping. (/docs/en/guides/simulate-with-qiskit-sdk-primitives; /docs/en/guides/primitives) → simulators-and-statevectors
- `StatevectorEstimator` is exact by default, based on `quantum_info.Statevector`. Passing `precision` adds shot-noise-style error. `StatevectorSampler` is exact by default too, and a `shots` argument introduces sampling. (/docs/en/guides/simulate-with-qiskit-sdk-primitives) → simulators-and-statevectors
- `Statevector` (`qiskit.quantum_info`): `from_instruction(circuit)` and `from_label` (labels 0, 1, +, -, r, l) build states. `evolve` applies an Operator or circuit. `probabilities` gives computational-basis probabilities. `sample_counts(shots)` samples without modifying the state. `expectation_value(oper)` is exact. `draw` supports text, latex, qsphere, hinton, bloch, city, and paulivec. (/docs/en/api/qiskit/qiskit.quantum_info.Statevector) → simulators-and-statevectors
- In 1.0, `UnitarySimulatorPy` and `StatevectorSimulatorPy` were replaced by `quantum_info.Operator` and `quantum_info.Statevector`. (/docs/en/guides/qiskit-1.0-features) → simulators-and-statevectors
- Aer (`qiskit_aer`, needs v0.14+) provides `EstimatorV2` and `SamplerV2` in `qiskit_aer.primitives`. Circuits must be transpiled for `AerSimulator`, e.g. `generate_preset_pass_manager(3, AerSimulator())`. Aer primitives lack some IBM options, such as resilience level. (/docs/en/guides/simulate-with-qiskit-aer) → simulators-and-statevectors
- Noise example: the ZZ...Z expectation on an 8-qubit `efficient_su2` circuit is about 0.887 when exact, and about 0.725 with 2% depolarizing error on each CX. Rough survival of the correct state is (1-p)^m for m CX gates. `NoiseModel` with `add_all_qubit_quantum_error(depolarizing_error(p, 2), ["cx"])`. (/docs/en/guides/simulate-with-qiskit-aer) → simulators-and-statevectors
- Local testing mode (needs runtime 0.22.0+) lets the same code run locally by swapping the backend. Backends are fake backends (`qiskit_ibm_runtime.fake_provider`, e.g. `FakeManilaV2`, with a snapshot of coupling map, basis gates and noise) or `AerSimulator` (`AerSimulator.from_backend(real_backend)` builds noise from calibration data). (/docs/en/guides/local-testing-mode) → simulators-and-statevectors
- `AerSimulator` methods: automatic (default), statevector, density_matrix, stabilizer (Clifford, very large circuits), extended_stabilizer, matrix_product_state, unitary, superop, tensor_network (GPU only). (/docs/en/guides/local-testing-mode; /docs/en/guides/local-simulators) → simulators-and-statevectors
- Limits of local simulation: noisy simulation cost grows exponentially with qubit count, and most laptops cannot go much beyond about 32 qubits. The Aer noise model is likely milder than real hardware, and `Session` is accepted but ignored. (/docs/en/guides/local-testing-mode) → simulators-and-statevectors, nisq-era
- Local mode vs dry-run jobs: a fake backend runs locally with no account and gives noisy simulation. A dry-run job on a mock device runs in the cloud (Flex/Premium/On-Prem plan), returns random data with the right schema, and reports `job.usage()`. (/docs/en/guides/local-testing-mode) → simulators-and-statevectors, running-on-hardware
- ⚠️ Not found in the docs read: the explicit 2^n memory formula for statevector simulation (the Statevector API page has no memory discussion). The only support is the exponential-cost and roughly 32-qubit remarks above.

## transpilation
- Transpilation rewrites a circuit to fit a specific device's topology and optimizes it for noisy hardware. The transpiler is modular, with passes chained in `PassManager` and `StagedPassManager`. (/docs/en/guides/transpile) → transpilation
- An ISA circuit uses only instructions in the backend `Target` (basis gates, measurements, resets, control flow) and respects the `CouplingMap`. Circuits submitted to IBM backends must be ISA. (/docs/en/guides/transpile; /docs/en/guides/intro-to-patterns) → transpilation
- Six stages. `init` validates and breaks multi-qubit gates into 1- and 2-qubit gates. `layout` maps virtual to physical qubits. `routing` inserts SWAPs for the coupling map. `translation` converts to basis gates. `optimization` loops until a condition (e.g. target depth) is met. `scheduling` is hardware-aware, accounts for idle time, and is applied only if a method is given. (/docs/en/guides/transpile) → transpilation
- `optimization_level` takes 0, 1, 2 or 3. Higher levels give better circuits but take longer to compile. (/docs/en/guides/transpile) → transpilation
- Recommended entry point: `generate_preset_pass_manager(backend=..., optimization_level=...)` from `qiskit.transpiler`, which returns a `StagedPassManager`. Call `pm.run(circuit)` to get the ISA circuit. Used in preference to `transpile()`. (/docs/en/guides/transpile; /docs/en/guides/hello-world) → transpilation
- After transpilation, observables must be mapped to the physical layout with `observable.apply_layout(isa_circuit.layout)`. (/docs/en/guides/hello-world) → transpilation, primitives-sampler-estimator
- The transpiler's goal is lower depth and complexity, to reduce noise effects. ⚠️ This page does not explicitly discuss two-qubit gate counts. The mitigation page says most hardware errors occur on two-qubit gates (/docs/en/guides/configure-error-mitigation). → transpilation
- 2.0 removals: `backend_properties`, `instruction_durations`, `timing_constraints`, `inst_map`, and custom `basis_gates` are no longer accepted by the transpiler. Use a `target`, a backend, or `Target.from_configuration`. Passing `coupling_map` or `basis_gates` together with a `backend` warns. (/docs/en/guides/qiskit-2.0) → transpilation
- Parameterized circuits can be transpiled once at `optimization_level=3` and then bound many times. (/docs/en/guides/construct-circuits) → transpilation, qiskit-circuits

## primitives-sampler-estimator
- Sampler samples the output register (bitstrings). Estimator computes expectation values of observables on the state a circuit prepares. These are the two most common tasks. (/docs/en/guides/primitives) → primitives-sampler-estimator
- V2 is recommended over V1: `BaseSamplerV2` and `BaseEstimatorV2`. In 1.0, `Sampler`/`Estimator` became `StatevectorSampler`/`StatevectorEstimator`. V2 Sampler returns bitstrings keyed by classical register name, not quasi-probabilities. V2 Estimator adds a `precision` argument. (/docs/en/guides/primitives; /docs/en/guides/qiskit-1.0-features) → primitives-sampler-estimator
- Implementations: reference (`StatevectorSampler`/`Estimator`), wrappers for any backend (`BackendSamplerV2`/`BackendEstimatorV2`), Aer, and IBM Runtime `Sampler`/`Estimator`. The `run()` interface is common but options differ. (/docs/en/guides/primitives) → primitives-sampler-estimator
- Runtime 0.50.0 introduced client-side primitives (`qiskit_ibm_runtime.executor_sampler.Sampler`, `executor_estimator.Estimator`), with suppression and mitigation run locally. Before that, `Sampler`/`Estimator` were server-side. (/docs/en/guides/local-testing-mode; /docs/en/guides/hello-world) → primitives-sampler-estimator
- PUB (primitive unified bloc) is one tuple per circuit. Estimator PUB is (circuit, observables, parameter values, optional precision). Sampler PUB is (measured circuit, parameter values, optional shots). (/docs/en/guides/primitive-input-output) → primitives-sampler-estimator
- Observables are `Pauli`, `SparsePauliOp`, `PauliList` or `str`, arranged in an array. Commuting observables in different PUBs are measured separately, so group them in one PUB to share measurements. (/docs/en/guides/primitive-input-output) → primitives-sampler-estimator
- Inputs broadcast with NumPy rules. A single `SparsePauliOp` counts as one element. An Estimator returns one value per element of the broadcast shape. (/docs/en/guides/primitive-input-output) → primitives-sampler-estimator
- Results: `job.result()` returns a `PrimitiveResult` with one `PubResult` per PUB. Estimator `data` has `evs` and `stds`. Sampler `data` is a `DataBin` with one `BitArray` per classical register (`meas` by default), read with `get_counts()`. `BitArray` also offers `slice_bits`, `slice_shots`, `expectation_values`, and mask indexing for post-selection. (/docs/en/guides/primitive-input-output; /docs/en/guides/hello-world) → primitives-sampler-estimator
- Shots and precision: Sampler shots are set per PUB or in `run()`. Estimator precision is per PUB. In the client-side Estimator, `options.default_shots` sets the shots (example 5000). (/docs/en/guides/qiskit-1.0-features; /docs/en/guides/hello-world) → primitives-sampler-estimator

## running-on-hardware
- Setup needs an IBM Cloud account and an IBM Quantum Platform login. Each account has instances identified by a CRN, tied to a region (which fixes where jobs run). One API key works in all regions. (/docs/en/guides/cloud-setup) → running-on-hardware
- `QiskitRuntimeService(channel, token, instance)`. The default channel is `ibm_quantum_platform`, and `channel="local"` needs no authentication. If `instance` is omitted, the service picks one. (/docs/en/guides/initialize-account) → running-on-hardware
- Save credentials once with `QiskitRuntimeService.save_account(token=..., instance=...)`, then later call `QiskitRuntimeService()`. (/docs/en/guides/hello-world) → running-on-hardware
- Choose a backend with `service.least_busy(simulator=False, operational=True, min_num_qubits=...)`. (/docs/en/guides/hello-world) → running-on-hardware
- Qiskit patterns, four steps. Map: turn the problem into circuits/operators. Optimize: transpile to an ISA circuit for the device. Execute: run with Sampler or Estimator, optionally in a Batch or Session with suppression/mitigation. Post-process: combine results (visualization, readout mitigation, marginalizing, post-selection). (/docs/en/guides/intro-to-patterns) → running-on-hardware
- Hello-world flow: build a Bell circuit, define `SparsePauliOp` observables, transpile, run `estimator.run([(isa_circuit, mapped_observables)])`, get `job.job_id()` (jobs can be retrieved later), and read `evs` and `stds`. A 100-qubit GHZ example follows. (/docs/en/guides/hello-world) → running-on-hardware
- Execution modes, chosen with `mode=`. Job (`backend`) is a single primitive request. Batch is independent jobs submitted together, not guaranteed in order, with no exclusive access. Session gives exclusive access, suits iterative work, and also blocks calibration jobs. (/docs/en/guides/execution-modes) → running-on-hardware
- Queueing: in batch and session, the first job still waits in the normal queue, so neither helps a single job. A maximum TTL starts at the first job, and an interactive TTL restarts after each job. When the TTL ends, queued jobs fail. (/docs/en/guides/execution-modes) → running-on-hardware
- Open Plan users cannot submit session jobs, and dry-run jobs do not support session mode. (/docs/en/guides/execution-modes; /docs/en/guides/run-jobs-session) → running-on-hardware
- For small circuits you can avoid the queue by using a fake backend such as `FakeBelemV2`. (/docs/en/guides/hello-world) → running-on-hardware, simulators-and-statevectors

## error-mitigation
- ⚠️ The docs do not give a formal definition of error suppression, mitigation or correction, and error correction is not mentioned on the overview page. Usage: suppression reduces the effect of noise during execution (e.g. dynamical decoupling), and mitigation estimates cleaner results from noisy runs (e.g. ZNE). (/docs/en/guides/error-mitigation-overview) → error-mitigation
- Dynamical decoupling (suppression): inserts identity-equivalent pulse sequences on idle qubits. It helps circuits with idle gaps, but in dense circuits it may not help and can hurt. Enabled via the DD transpiler pass or `options.dynamical_decoupling.enable` (`sequence_type`, e.g. `"XY4"`). (/docs/en/guides/error-mitigation-and-suppression-techniques; /docs/en/guides/configure-error-mitigation; /docs/en/guides/hello-world) → error-mitigation
- Pauli twirling: random Pauli gates around gates (usually two-qubit) make an ensemble of circuits with the same ideal effect, which turns noise into Pauli form. Enabled via `options.twirling.enable_gates` (`num_randomizations`, `shots_per_randomization`). (/docs/en/guides/configure-error-mitigation; /docs/en/guides/estimator-noise-management) → error-mitigation
- TREX: randomizes measurements to diagonalize the readout-error matrix, then corrects expectation values of Pauli observables. Option `resilience.measure_mitigation`. Small overhead from calibration circuits. (/docs/en/guides/error-mitigation-and-suppression-techniques) → error-mitigation
- ZNE: runs the circuit at amplified noise (digital gate folding) and extrapolates to zero noise (linear or exponential fit). It may be biased. Default of three noise factors costs roughly 3x. Options `resilience.zne_mitigation`, `noise_factors`, `extrapolator`. (/docs/en/guides/configure-error-mitigation; /docs/en/guides/estimator-noise-management) → error-mitigation
- PEA: learns the noise of each entangling layer and amplifies it probabilistically before ZNE extrapolation. Needs ZNE enabled (`zne.amplifier = "pea"`). Often best for utility-scale experiments. (/docs/en/guides/error-mitigation-and-suppression-techniques; /docs/en/guides/estimator-noise-management) → error-mitigation, nisq-era
- PEC: gives an unbiased estimate by sampling noisy circuits from a quasi-probability decomposition. Sampling overhead grows as γ², and γ grows exponentially with depth, so it is generally costlier than ZNE. Option `resilience.pec_mitigation` (`max_overhead`). (/docs/en/guides/error-mitigation-and-suppression-techniques; /docs/en/guides/error-mitigation-overview) → error-mitigation
- `resilience_level`: 0 means no mitigation. 1 (default) means TREX readout mitigation, with minimal cost. 2 means level 1 plus ZNE and gate twirling, at medium cost. Level 2 usually reduces bias but is not guaranteed zero-bias. Levels are in beta, and explicit options override the level (e.g. setting `zne_mitigation = True` at level 0). Set via `Estimator(backend, options={"resilience_level": 2})` (server-side) or `estimator.options.resilience_level` (client-side). (/docs/en/guides/estimator-noise-management; /docs/en/guides/hello-world) → error-mitigation
- With the client-side Estimator (runtime 0.50.0+), PEA and PEC need a separate noise-learning job. `NoiseLearnerV3` (introduced in 0.47.0) is the current helper. The legacy `NoiseLearner` (from 0.27.1) works only server-side and is deprecated since 0.51.0. (/docs/en/guides/noise-learning) → error-mitigation
- Where the techniques are available: Qiskit addons (e.g. Qiskit Mitigation, noise-learning addon) for your own workflow, or IBM Quantum Compute Service applying them at submission. Local testing mode has no built-in mitigation, so options must be set explicitly. (/docs/en/guides/error-mitigation-overview; /docs/en/guides/local-testing-mode) → error-mitigation

## variational-algorithms
- Variational loop: a classical optimizer (e.g. SciPy `minimize` with COBYLA) calls a cost function that sends circuits to the QPU. Sessions suit this because they allow frequent classical-quantum exchange. (/docs/en/guides/run-jobs-session) → variational-algorithms
- Session usage: `Session(backend=backend)` passed as `mode=session`. Set `max_time` longer than the longest job (default max TTL 8 hours on Premium, interactive TTL 60 s). Close with `session.close()` or a context manager, and queued jobs still run. Job tags via `options.environment.job_tags`. (/docs/en/guides/run-jobs-session) → variational-algorithms, running-on-hardware
- VQE tutorial: a 10-qubit `efficient_su2` ansatz (`reps=2`), a 10-spin Heisenberg Hamiltonian as `SparsePauliOp`, and `EstimatorV2` returning `data.evs`. A custom SPSA optimizer (not SciPy) needs 2 cost evaluations per iteration. All runs sit inside one session. `maxiter=50` used 101 evaluations and reached about -3.038. (/docs/en/tutorials/variational-quantum-eigensolver) → variational-algorithms
- The VQE tutorial follows the four patterns steps: map the ansatz and Hamiltonian, optimize with `optimization_level=3` plus ALAP scheduling and dynamical decoupling, execute inside a session, post-process the energy history. It needs Qiskit 2.0+ and runtime 0.44+. (/docs/en/tutorials/variational-quantum-eigensolver) → variational-algorithms, transpilation
- Parameterized circuits are built once and transpiled once, then rebound at each step. (/docs/en/guides/construct-circuits) → variational-algorithms
- In 1.0, the `algorithms` and `opflow` modules were removed from Qiskit (the docs say `qiskit.utils` helpers that supported them were removed). (/docs/en/guides/qiskit-1.0-features) → variational-algorithms
- Qiskit Functions catalog lists partner functions, including `/docs/guides/qunova-chemistry` (HI-VQE chemistry) and optimization functions (Kipu, Q-CTRL, and others). (/docs/en/guides) → variational-algorithms

## nisq-era
- ⚠️ The guides do not discuss NISQ or utility-scale in prose, and the error-mitigation overview and noise-learning pages do not mention utility-scale. The remarks below are all the docs support.
- PEA is described as often the best mitigation choice for utility-scale experiments. (/docs/en/guides/error-mitigation-and-suppression-techniques) → nisq-era, error-mitigation
- Noise limits what hardware can do. Circuits are optimized to minimize noise, noise decays correlations as the GHZ test circuit grows (the 100-qubit GHZ example shows the decay of ZZ correlators), and mitigation overheads (ZNE about 3x, PEC exponential in depth) cap what is practical. (/docs/en/guides/transpile; /docs/en/guides/hello-world; /docs/en/guides/error-mitigation-and-suppression-techniques) → nisq-era
- Classical simulation can't follow beyond a few dozen qubits with noise (~32 on a laptop), so large hardware runs can't be checked this way. (/docs/en/guides/local-testing-mode) → nisq-era, simulators-and-statevectors
- Search-result snippet only, not read in full: the Qedma QESEM function runs a 136-qubit Kicked Ising circuit on ibm_fez (/docs/en/guides/qedma-qesem), and a tutorial on utility-scale PEA exists (/docs/en/tutorials/probabilistic-error-amplification). → nisq-era

## Functions and addons (brief)
- Qiskit Functions are partner-built services (circuit functions such as Algorithmiq TEM, Q-CTRL, Qedma QESEM, and application functions for optimization and chemistry), plus templates for chemistry, Hamiltonian simulation, and AQC-Trotter. (/docs/en/guides) → running-on-hardware
- Qiskit addons: Qiskit Mitigation (ZNE/PEC/TREX), noise learning, sample-based quantum diagonalization (SQD, post-processing), and Samplomatic. Changelog at /docs/guides/changelog-qiskit-addons. (/docs/en/guides) → error-mitigation
