## qiskit-circuits
- The circuit is the core component of Qiskit and the rest of the framework revolves around it (Fig. 2, p. 5). A circuit is a time-ordered set of instructions (§III.A, p. 4). (p. 4) → qiskit-circuits
- Circuits are defined broadly: any operation on quantum or classical data. This includes resets, gates and measurements, and also higher-level operators such as unitaries, isometries, Cliffords and Fourier transforms (§III.A, p. 4). → qiskit-circuits
- Circuits can include real-time classical computation on measurement outcomes (e.g. Boolean functions) and real-time control flow (loops, branching) while qubits stay coherent (§III.A, pp. 4-5). → qiskit-circuits
- Circuits can also describe operation timing and continuous-time qubit dynamics through pulse-defined gates. Different abstraction levels can be mixed in one circuit, and circuits compose like building blocks (§III.A, p. 5). → qiskit-circuits
- Design goal "interoperability across abstraction levels": users may program at high level or at the level of gate timing and dynamics, all compatible in the same circuit. Cross-layer optimizations are possible, e.g. synthesizing high-level operators directly for a Target without intermediate steps that lengthen depth (§II.4, p. 3). → qiskit-circuits
- "Dynamic circuits" are those whose executed instructions are decided as the circuit runs, using real-time classical computation (e.g. control flow on measurement results) while qubits are coherent. The model resembles that of OpenQASM 3 (§II.5, p. 3). → qiskit-circuits
- Abstraction levels in the software stack (Fig. 1, p. 2): (a) problem, (b) abstract circuit (e.g. exponentials of Paulis, high-level operators), (c) circuit with standard-library gates after synthesis, (d) ISA circuit with explicit gates and schedule, (e) code generation for runtime/controller. Qiskit's scope is the "middle-end" from (b) to (d). → qiskit-circuits
- Fig. 3 (p. 6) gives four example circuit kinds: standard gates with classical control flow (entanglement distillation with an if statement), parameterized circuits (twirled Trotter evolution that can be instantiated by substituting parameters), high-level abstract composition (quantum phase estimation with controlled powers of a unitary and a QFT, whose synthesis is left to the transpiler), and hardware-native gates with timing (GHZ with dynamical decoupling). → qiskit-circuits
- Internal representations: default is a list of instructions. Many rewriting algorithms prefer a DAG data-flow graph, which makes the order of operations and information flow explicit. A canonical form accounting for gate commutation (only true dependencies) also exists. Structured sub-circuits can be temporarily converted to specialised forms (Boolean linear functions, Cliffords, phase polynomials) (§III.A, p. 5). → qiskit-circuits
- Circuits are kept lightweight: common gates are singletons in the standard library, blocks can be reused, and synthesis/lowering of abstract operations is deferred lazily to the transpiler (§III.A, p. 5). → qiskit-circuits
- Parameters: a circuit can use `Parameter` objects (example `Parameter('theta')` for X-rotation angle, §IV.B, p. 9); values are bound at runtime, and the parameter-binding framework lets hardware process one template with many substitutions (§IV.B, p. 7). → qiskit-circuits
- Code examples show dynamic-circuit constructs: `for_loop`, `if_test` with `qiskit.circuit.classical.expr` (e.g. `expr.bit_xor`, `expr.equal`) for classical expressions on measured bits (§IV.D, p. 10). A `switch` statement (evaluated once, exactly one case runs, so constant duration) is used in the experiment (App. A, p. 17). → qiskit-circuits
- Conventions: tensor products are ordered Q2⊗Q1⊗Q0 (little-endian), so Pauli ZX means Z on qubit 1 and X on qubit 0, and |001⟩ = |1⟩. For CX, Q0 is the control and Q1 the target, giving a matrix that may differ from some textbooks; using CX(Q1,Q0) in the circuit changes it. Instructions are drawn left to right in time, opposite to how matrices multiply (§II.9, p. 4). → qiskit-circuits
- Circuit library: the standard gate/circuit library is mentioned and can be extended (e.g. via plug-ins), with blocks such as Pauli evolution, unitary, isometry, SU(4) shown in Fig. 2 (p. 5; §II.1, p. 3). The paper gives no detailed catalogue. → qiskit-circuits
- Ecosystem examples show circuits used for qudits, bosonic modes, measurement-based and Pauli-based computation, and noise channels (§V, pp. 11-12). → qiskit-circuits

## simulators-and-statevectors
- The `quantum_info` module connects circuits to the mathematical formalism: states (Statevector, density matrix, stabilizer state), operators (Unitary, Clifford, Pauli), channels (Choi, PTM, SuperOp), measures/distances (Fig. 2 and caption, p. 5). It includes operators usable to build abstract circuits or as observables. → simulators-and-statevectors
- `SparsePauliOp.from_sparse_list` is used to define the average-magnetization observable (1/N)ΣZ_i (§IV.B, p. 9); `apply_layout` maps an observable to the transpiled circuit's physical qubits (§IV.D, p. 11). → simulators-and-statevectors
- Backends for primitives "may consist of simulators or hardware" (Fig. 2 caption, p. 5). High-performance simulators (e.g. Qiskit Aer GPU work, Qulacs) are mentioned only as ecosystem packages built on Qiskit (§V, p. 11). The paper itself does not describe simulation methods or give statevector details. → simulators-and-statevectors

## transpilation
- Scope: the transpiler rewrites circuits in several rounds of passes to optimize and translate them to the target ISA. "Transpiler" stresses that it is circuit-to-circuit, distinct from full compilation to controller binaries, but it can be viewed as an optimizing compiler (§II, p. 1). → transpilation
- The ISA is the key abstraction layer between hardware and software. For superconducting qubits it can include CNOT, √X and RZ(θ). For logical machines it could include joint Pauli measurements or magic-state distillation. It often also includes measure, reset, delay, control flow and limited classical computation (§II, p. 1). → transpilation
- Heron ISA (App. B, Table I, p. 18): RZ(θ), SX, X, DELAY, MEASURE, RESET, INIT, CZ, BARRIER, IF/ELSE, SWITCH, FOR, WHILE. CZ is allowed only on edges of the connectivity graph. This is a concrete example of an ISA circuit's gate set (133-qubit Heron, tunable couplers). → transpilation
- Pass Manager: the transpiler is a collection of proven translation and optimization passes on a framework to describe, compose and run pipelines of circuit transformations. The infrastructure (PassManager) builds and runs composable, reusable pipelines of semantics-preserving transformations, with logic that can steer the flow based on device, circuit or intermediate properties. It resembles classical compiler infrastructure such as LLVM (§III.B, p. 6). → transpilation
- The transpiler's output is itself a quantum circuit, so transpiled circuits can be inspected and modified with the same tools used to build them (§III.B, p. 6). → transpilation
- Qiskit defines standardized compilation stages, each made of transformation and analysis passes. These give hook points for plugins to modify or extend the predefined pass managers shipped with Qiskit; these encapsulate best practice and serve as a basis for full-pipeline performance comparisons (§III.B, pp. 6-7). → transpilation
- Stages named in the paper: synthesis, routing, optimization, scheduling (Fig. 1, p. 2); layout, routing, optimization, scheduling (Fig. 2, p. 5). The paper does not name init/translation stages explicitly in prose and gives no per-stage description. ⚠️ → transpilation
- Code: `generate_preset_pass_manager(target=..., optimization_level=3)` builds the preset pipeline. The user appends passes to the scheduling stage (`pm.scheduling += PassManager([ALAPScheduleAnalysis, PadDynamicalDecoupling])`) to insert dynamical decoupling, and can fix `initial_layout`. `pm.run(circuits)` returns ISA circuits (§IV.B and §IV.D, pp. 9, 11). → transpilation
- Retargetability: the transpiler adapts to non-standard and heterogeneous gate sets. Adding a partial ZX (RZX) gate with its duration and error to the Target leads the transpiler to re-synthesize ZZ(θ) interactions into ZX(φ), shortening circuits. The new gate need not be calibrated on all edges, as it is used opportunistically (§IV.C, pp. 9-10). → transpilation
- Routing example: mapping a honeycomb lattice onto heavy-hex hardware via the transpiler needs SWAP gates. A dynamic-circuit alternative using ancillas, mid-circuit measurement and feed-forward gave shorter depth and slightly better results (§IV.D, pp. 10-11; Fig. 4). → transpilation
- Fig. 1 example: a peephole optimization reduces a subcircuit from CNOT-depth 26 to 12 (caption, p. 2). → transpilation
- Performance: performance-critical code is written in Rust (about 6% of the code base), with benchmarks tracked over time. Python remains the user-facing language (§II.2, p. 3). Rust is also used for transpilation, giving scalability to large circuits (§IV.B, p. 7). RustworkX is the graph library (§IV.B, p. 7). → transpilation
- Plugin interface: external synthesis and optimization methods, even outside Qiskit, can plug in. Ecosystem examples include plugin transpiler passes (e.g. alternative qubit routing / mapping, SAT synthesis) (§II.1, p. 3; §V, p. 11). → transpilation
- Not covered in the paper: SabreLayout/SabreSwap, optimization-level definitions, basis-translation details, and benchmark comparisons against other SDKs. No such content is present. → transpilation

## primitives-sampler-estimator
- Two main primitives capture a circuit's output: sampling output bitstrings and estimating observable expectation values. They are the way circuits are evaluated in Qiskit and define a common interface even if implementations vary a lot (§II.6, p. 4). → primitives-sampler-estimator
- Interface: take a (possibly parameterized) ISA circuit plus one or more observables, and return expectation estimates. Different estimators (an active research area, including ones with error mitigation) can thus be exposed to Qiskit as primitives, i.e. effective executors for quantum computers (§II.6, p. 4). → primitives-sampler-estimator
- Samplers return measurement outcomes; estimators return post-processed expectation values (§III.C, p. 7). → primitives-sampler-estimator
- A unit of work for the estimator is a PUB (primitive unified block): one circuit with possibly several observables and parameter sets. Example: `estimator.run([(circ, [obs], params) for circ in circuits_isa])`; results via `.data.evs` (§IV.B, p. 9). → primitives-sampler-estimator
- Multiple parameter bindings to one circuit template are explicitly provisioned in the primitives interface (§IV.B, p. 7). → primitives-sampler-estimator
- Primitives take ISA circuits, so circuits must be transpiled first (§II.6, p. 4; workflow in §II.7). → primitives-sampler-estimator

## running-on-hardware
- Target: an abstract machine model describing the instructions available on hardware, their properties (timings, error rates) and other constraints. The transpiler uses it to optimize for a given backend, and it also supports different technologies (superconducting, trapped ion) (§II.3, p. 3; Fig. 2, p. 5). → running-on-hardware
- In code, the target is obtained from `backend.target` (the backend from `QiskitRuntimeService().backend(name)`), and a coupling map via `target.build_coupling_map()` (§IV.B, p. 7). The Target can be edited (`add_instruction` with `InstructionProperties` for duration and error) (§IV.C, pp. 9-10). → running-on-hardware
- Qiskit patterns: a four-step workflow (1) map the problem to circuits, (2) transpile to the target hardware, (3) execute with primitives on a backend, (4) post-process into a solution. Patterns can iterate (loop around the last three steps, e.g. variational), or embed quantum compute in large-scale classical compute (quantum-centric supercomputing). Qiskit serverless helps orchestrate complex patterns (§II.7, p. 4). → running-on-hardware
- Real-time versus near-time classical compute: real-time occurs while qubits are coherent (control flow on measurements). Near-time has looser timing but low latency (parameter binding, JIT compilation, parameter optimization, error mitigation). Qiskit is a lightweight framework meant to be integrated into a runtime that co-locates quantum and classical processors, e.g. Qiskit Runtime on IBM machines (§II.5, p. 3). → running-on-hardware
- Primitives can be implemented in a Qiskit runtime environment with tightly coupled near-time quantum-classical compute. Co-location lowers latency for tasks such as circuit optimization for error suppression, extra circuits for mitigation, post-processing and parameter updates (§III.C, p. 7). → running-on-hardware
- Execution flow: the transpiler only rewrites circuits. ISA circuits are serialized via OpenQASM for execution, while QPY is used for Qiskit-native objects for services. Final code generation for the controller happens in the runtime (Fig. 1e, p. 2; Fig. 2 caption, p. 5). → running-on-hardware
- Experiment: 127-qubit `ibm_pinguino1` (fixed-frequency transmons, heavy-hex, cross-resonance), used for kicked-Ising simulation on a 23-qubit subgraph (§IV.A, p. 7). Heron has 133 qubits and tunable couplers (App. B, p. 18). Hardware details: measurement took 1400 ns and feed-forward 1060 ns on the device; no gates run during feed-forward on that control electronics (App. A, p. 17). → running-on-hardware
- Limits of current execution model: the Heron ISA gives no timing for classical expressions or control-flow branching, and the execution model serializes all control flow, which hampers short dynamic circuits. Planned changes include equal-duration branches, no nested runtime control flow, countable loops, and OpenQASM "stretch" for timing intent (App. B, pp. 18-19). → running-on-hardware

## error-mitigation
- Many algorithms and mitigation protocols need many circuit executions, which motivates a focus on speed (§II.2, p. 3). → error-mitigation
- Error mitigation is listed as a near-time classical task; efficient estimators and mitigation methods that improve their results are an active research area (§II.5, p. 3; §II.6, p. 4). A cited example is the "utility" experiment that used error mitigation (§I, p. 1; ref. [51]). → error-mitigation
- In the example the Estimator is run with built-in readout error mitigation: `EstimatorOptions(optimization_level=0, resilience_level=1)` (Fig. 4 caption, p. 8; §IV.B, p. 9). The paper does not define what each resilience level does. → error-mitigation
- The authors did not apply mitigation methods that incur large sampling overhead (such as probabilistic error cancellation, ref. [93]), though these are expected to extend computational reach. They used error suppression instead (§IV.D, p. 11). → error-mitigation
- Error suppression versus mitigation: dynamical decoupling (inserted in the scheduling stage) refocuses coherent noise and suppresses incoherent noise to first order, and matters more in dynamic circuits because qubits sit idle during measurement and feed-forward (§IV.D, p. 11). → error-mitigation
- Dynamic-circuit suppression (App. A, p. 17): DD in parallel with measurement; replacing a series of if statements with one switch-case to give constant duration; and adding conditional inverse Z rotations in each branch to compensate static-crosstalk ZZ/Z accumulation. Ancilla reset is done by conditional X in each branch. This allowed 8 Trotter steps. → error-mitigation
